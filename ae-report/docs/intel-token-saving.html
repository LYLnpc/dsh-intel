怎么把额度花在真活上（不浪费 token 的消耗法）

generated_at: 2026-11-14T14:00:00+08:00 author: 调研员 用途：任务书第⑧条。给「额度快过期、想尽量烧在有产出的事上」的人看——不是省额度，是别把额度烧在假活上。 判据一句话：这份支出能不能落盘成别人（或未来的自己）能直接用的东西？能 = 真活；不能 = 空转。

一、本轮实战验证过的三条（新证据，排最前）

1. spec 驱动复刻：先写 6–12KB 功能说明，再让执行者照写

本轮 Scribe 就是活证据：码农先按商品摘要起手，做成「文字层转形状」；intel/specs/scribe.md 到位后，spec 直接指出版权红线（原版 6 套字型不能复刻、改用公有领域 Hershey）与正确架构，码农当场删掉重做。一份 5.8KB 的 spec 省掉一整版（≈18KB 代码）返工。

  • 成本：一件 spec ≈ 一次调研 + 6–12KB 落盘
  • 收益：执行阶段返工率显著下降；返工是最贵的 token 支出（写 + 验 + 改 三轮）
  • 做法：spec 必含「用户可见行为 / 参数表 / 复刻要点（含 API）/ 明确不做 / 验收点」五段。缺「明确不做」的 spec 等于没写——范围不收口，执行者必然发散。

2. 精确路径核验：每句「已落地」都要有命令输出兜底

本轮实账：我用 glob 扫 clones/ 报「trim-comp MISS」，换 Get-ChildItem 全量列目录才看清真实名字是 trim-comp-clone——错在匹配词，不在产物。同类事故还有一次更贵的：码农误判子 agent 未交件，重写了一份 19.7KB 的 limber2-clone/main.jsx 覆盖原件，靠 out/limber-clone/ 的备份才救回。

  • 规则：验收/进度统计只认「命令 + 输出」；不用印象、不用上次的列表。
  • 具体三件套：Get-ChildItem <dir> -Directory 列全量 → 逐目录 -File -Recurse 计数 → 与清单对账（数量差必须为 0 才能报「齐了」）。
  • 覆盖同伴文件前先 Test-Path + 读一遍；改内容用追加，换版本用 -full / -v2 新文件名。本轮为此废掉三份详细 spec 又靠备份救回，纯属可避免的支出。

3. 批次限流 + 402 即切：把额度当配额，不当水管

本轮子 agent 池的实测节奏：

  • 一次放 3 个子 agent（对应三个可并行件），不是放 9 个——9 个同时跑会互相等文件锁、且失败面不好定位
  • 三个模型轮着用（deepseek-v4.1-flash / deepseek-v4.1-flash-1017 / glm-5.3-flash），某模型返回 402 立刻切下一个，不重试同一模型
  • 三全 402 才算真死，才收工；单模型 402 只记录不喧哗
  • 好处：额度用尽前的最后一刻仍在出活，而不是卡在一个死掉的 provider 上反复超时

二、值得主动多烧的「真活」清单

按「每千 token 的落地价值」排序：

活儿单次产出量级为什么值
交叉评审一轮（两人互审对方产物）15–25KB本轮实际抓出：deleteKey 不存在、枚举大小写 ONE_D 错拼、getHavingSaved 被当值用、撤销组双 end。这类错 node --check 查不出、运行才炸
新件复刻（每件 main.jsx + README）60–110KB唯一能直接进交付物的支出
深度检索补情报（价格/替代/教程/踩坑）10–20KB直接进网页「价值清单/替代方案」两节，可反复引用
把长报告压成结构化表（MD 表 / JSON）5–15KB一次压缩，后续所有汇总都便宜；网页、记忆、总结三处复用
写 spec（功能行为说明）6–12KB见 §1.1，摊薄返工
回归/冒烟脚本（如 AE 实机冒烟清单）5–10KB一次写好，每批产物复用；比人眼抽查可靠
第二版增强（给已有件加参数/修边界）20–40KB边际价值高（用户真正会用的常是第二版）
离线自检（网页/产物可打开、路径可达、计数勾稽）5–10KB交付前的最后一道闸，成本极低

三、看着像活、其实是空转的（别烧）

  1. 同一条信息重复检索——先 cache_search 查本地缓存（保留 7 天），命中就别再打一次 API。
  2. 把已落盘的内容再抄一遍（比如把 intel/ 里已有的表挪进另一个文件）——用链接指过去就行。
  3. 空转催办（「进度如何了」）——改成要一份可验收的产物或状态清单。
  4. 无验收标准的「再优化一版」——没有「不过就打回」的条目，优化没有终点，这是最容易吃掉大额度的黑洞。
  5. 一次放太多并行 agent——互相等依赖、重复读同批文件，实际吞吐反而下降。
  6. 在死掉的 provider 上重试——402/超时就是答案，切走。
  7. 为了「让输出更长」而扩写——长不等于有用；判断标准是有没有新增可验收的信息。

四、额度快过期时的收尾顺序（照着走，不留半成品）

  1. 手头在写的件写完（半成品等于零）
  2. 打最终包 / 落最终报告（可发布状态）
  3. 出总结（做了什么、没做什么、缺口在哪）
  4. 停；不做新的探索性尝试

本轮的落点正是这个顺序：9/9 复刻完成 → zip 打包 351,548B → 等用户发话再发布。

五、一句话总结

额度不是用来「跑满」的，是用来「换产物」的。 每一笔支出问一句：这一轮结束后，磁盘上多了什么别人能直接用的东西？答不上来就停。
